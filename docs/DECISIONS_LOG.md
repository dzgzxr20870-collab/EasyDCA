## [Hotfix] - 29 สิงหาคม 2569 — `42702 ambiguous column` ใน RPC `set_default_portfolio_locked`

**อาการ:** กดปุ่ม "ตั้งเป็นพอร์ตหลัก" บน `/app` แล้วได้ `500 INTERNAL_ERROR` ทุกครั้ง

**Root Cause — บั๊ก PL/pgSQL คลาสสิก:**
`set_default_portfolio_locked` (migration 048) ประกาศ
`RETURNS TABLE (id, user_id, name, type, is_default, created_at, updated_at)`
ซึ่งทำให้ชื่อเหล่านี้กลายเป็น **ตัวแปร OUT ที่มองเห็นได้ทั้งฟังก์ชันโดยอัตโนมัติ**
ภายในฟังก์ชันมี `UPDATE public.portfolios SET ... WHERE user_id = p_user_id`
ที่อ้าง `user_id` แบบไม่ใส่ Alias → Postgres แยกไม่ออกระหว่างคอลัมน์ของตารางกับ
ตัวแปร OUT ชื่อเดียวกัน → `42702 column reference "user_id" is ambiguous`

**ทำไมไม่เจอมาก่อน:** ฟีเจอร์ "ตั้งพอร์ตหลัก" เพิ่งถูกใช้งานจริงเป็นครั้งแรกในเซสชันนี้
— ก่อนหน้านี้ผู้ใช้ทุกคนมีพอร์ตเดียว จึงไม่เคยมีเหตุต้องสลับพอร์ตหลักเลย บั๊กจึงซ่อน
อยู่ตั้งแต่ Apply migration 048 โดยไม่มีใครรู้

> ⭐ **บทเรียนที่สำคัญกว่าตัวบั๊ก:** `CREATE FUNCTION` ผ่าน **ไม่ได้แปลว่าฟังก์ชัน
> ใช้งานได้** — Postgres ตรวจแค่ Syntax ตอนสร้าง ไม่ได้ Resolve ชื่อคอลัมน์ให้จนกว่า
> จะรันจริง "Apply migration ผ่าน" จึงไม่ใช่หลักฐานว่าของใช้ได้ ต้องเรียกใช้จริง
> อย่างน้อย 1 ครั้งเสมอ (สอดคล้องกับ DoD ชั้น 4 ใน `AI_WORK_POLICY.md` § 3)

**การแก้:** เพิ่ม Alias `pf` ให้ `public.portfolios` ใน **ทั้งสอง** `UPDATE` statement
ภายในฟังก์ชัน แล้วอ้างทุกคอลัมน์ผ่าน `pf.column_name` แทนชื่อเปล่าๆ — แก้ที่ Supabase
SQL Editor โดยตรงด้วย `CREATE OR REPLACE FUNCTION` ทับของเดิม

- **ไม่กระทบข้อมูลเดิมแม้แถวเดียว** (เปลี่ยนเฉพาะนิยามฟังก์ชัน ไม่แตะ Schema/Data)
- **ไม่ต้องแก้/Redeploy โค้ด Backend** เพราะ RPC ถูกเรียกผ่าน Interface เดิมทุกประการ

**⚠️ ห้ามแก้ `backend/migrations/048_*.sql` ย้อนหลัง** — ไฟล์ Migration ที่ Apply ไปแล้ว
เป็น Immutable Record ของ "สิ่งที่เคยถูก Apply จริง" ถ้าแก้ย้อนหลังจะอ่านประวัติไม่ตรง
กับความจริงของ DB (ไฟล์ในนี้จึงยังมีบั๊กอยู่ตามเดิมโดยเจตนา)

**Known Issue ที่ยังไม่แก้ (บันทึกไว้เตือน):**
`create_portfolio_locked` — Function พี่น้องกันใน migration 048 — มี Pattern เดียวกัน
(`RETURNS TABLE` ที่ชื่อคอลัมน์ชนกับตารางได้) แต่ **ยังไม่เจอบั๊กจริง** เพราะทุกจุดที่
อ้างคอลัมน์ในฟังก์ชันนั้นมี Alias กำกับอยู่แล้ว (`p.user_id`) หรืออยู่ในบริบทที่ไม่กำกวม
(INSERT column list) — **ไม่ต้องแก้ตอนนี้** แต่ถ้าแก้ฟังก์ชันนั้นในอนาคตต้องระวัง
Pattern เดียวกัน (Checklist อยู่ที่ [`AI_WORK_POLICY.md` § 4.5](./AI_WORK_POLICY.md))

**เรื่อง Repo/DB Drift ที่ตรวจระหว่างทาง — สมมติฐานแรกผิด:**
ระหว่างวินิจฉัยเคยตั้งสมมติฐานว่าอาจเป็น Drift ระหว่างไฟล์ใน Repo กับของจริงบน
Supabase · ตรวจแล้ว **ไม่ใช่** — ไฟล์ migration 048 ในเซสชัน SQL Editor ของ Supabase
(แท็บ "048" ที่ Founder เคย Save ไว้) มีเนื้อหาตรงกับ Repo เป๊ะ รวมถึงบั๊กตัวนี้ด้วย
แปลว่าบั๊กอยู่มาตั้งแต่ Apply ครั้งแรก ไม่ได้เกิดจากใครไปแก้ของจริงแล้วลืม Sync กลับ

## [Decided] - 24 สิงหาคม 2569 — กติกา `portfolioId`: `undefined` / `null` / `uuid`

**ไม่มีอยู่ใน Design Doc § 8** — เกิดตอนรีวิวโค้ดหลัง Stage 8 เมื่อพบว่า
`migration 044` จะทำให้ระบบพัง 4 จุดทันทีที่ Apply
(Post-mortem เต็ม: [`POSTMORTEM_PORTFOLIO_RESOLUTION.md`](./POSTMORTEM_PORTFOLIO_RESOLUTION.md))

| ค่า | ความหมาย | พฤติกรรม |
|---|---|---|
| `undefined` | **"ยังไม่ระบุ / พอร์ตไหนก็ได้"** | ไม่กรอง `portfolio_id` เลย — คืนทุกแถวของ Symbol นั้นข้ามพอร์ต |
| `null` | **"เจาะจงว่าไม่มีพอร์ต"** | `.is('portfolio_id', null)` |
| `'<uuid>'` | เจาะจงพอร์ตนั้น | `.eq('portfolio_id', uuid)` |

> ⭐ **นี่ไม่ใช่ Pattern ใหม่** — เป็นกติกาเดียวกับ `brokerId` ที่ Stage 5 วางไว้แล้ว
> ทุกประการ · สิ่งที่ทำคือ "ทำให้ `portfolioId` ใช้กติกาเดียวกับ `brokerId`"
> ไม่ใช่การคิดกติกาขึ้นใหม่

**มติที่ตามมา 2 ข้อ:**

| # | คำถาม | มติ |
|---|---|---|
| 1 | ซื้อ Symbol **ใหม่** โดยไม่ระบุพอร์ต → ลงพอร์ตไหน | **พอร์ต Default** (`is_default`) · เป็นพฤติกรรมที่ตรงกับก่อน 044 มากที่สุด และเส้นทาง LINE ไม่มีคอนเซ็ปต์พอร์ตเลย · **ไม่ใช่ Silent Default** เพราะกรณีกำกวมจริง (ถือ Symbol นี้อยู่แล้วในพอร์ตอื่น) ถูก `AMBIGUOUS_ASSET_PORTFOLIO` ดักไปก่อนแล้ว — มาถึงจุดนี้ได้แปลว่า "ยังไม่เคยถือที่ไหนเลย" ซึ่งไม่มีอะไรให้กำกวม |
| 2 | ถือ Symbol เดียวกันอยู่หลายพอร์ต แล้วไม่ระบุพอร์ต | **`AMBIGUOUS_ASSET_PORTFOLIO` (409) — ถาม/Reject ห้ามเดา** (กฎยืนข้อ 11) · ตรวจมิติ "พอร์ต" **ก่อน** มิติ "โบรก" เสมอ เพราะพอร์ตหยาบกว่า (โบรกเดียวกันอาจอยู่ได้ทั้งสองพอร์ต ถามโบรกก่อนจะสับสน) |

**เหตุผลที่ข้อ 2 ต้อง Reject ไม่ใช่เดา:** ถ้าเงียบๆ ไปสร้างแถวใหม่ในพอร์ต Default
ทั้งที่ผู้ใช้ถือ Symbol นั้นอยู่ในพอร์ตอื่นแล้ว = **ประวัติแตกไปคนละ `asset_id`**
ซึ่งคือบั๊กเดียวกับที่ `migration 014` สร้างมาแก้ กลับมาในรูปใหม่

> ✅ **อัปเดต 27 ส.ค. 2569 — ปุ่มเลือกพอร์ตบน LINE ทำเสร็จแล้ว**
> (`buildPortfolioPickerMessage` + Postback `pick_portfolio`) หมายเหตุเดิมที่ว่า
> "ฝั่ง LINE ยัง Reject อย่างเดียว ให้ไปใช้เว็บแทน" **ไม่เป็นจริงอีกต่อไป**
> — ดูมติ 27 ส.ค. 2569 ด้านล่าง

## [Decided] - 28 สิงหาคม 2569 — ลบตาราง `_backup_044_assets_portfolio` ทิ้ง

**ตัดสินใจ: ลบได้ ไม่ต้องเก็บ** — และนี่ไม่ใช่การยอมรับความเสี่ยง แต่เป็นข้อสรุปจาก
การดูสภาพข้อมูลจริงก่อน Backfill

### เหตุผล: สภาพก่อน `044` reconstruct ได้ 100% โดยไม่ต้องมี Backup

ก่อน Apply `044` ข้อมูลอยู่ในสภาพนี้เป๊ะ:

- `portfolios` = **0 แถว** (ตารางมีอยู่ใน Schema ตั้งแต่วันแรกแต่ไม่เคยถูกใช้)
- `assets.portfolio_id` = **NULL ทุกแถวโดยไม่มีข้อยกเว้น** (เพราะไม่มีพอร์ตให้ผูก)

→ การ "กู้คืน" สภาพเดิมจึงเท่ากับ `UPDATE assets SET portfolio_id = NULL` +
ลบพอร์ตที่ Backfill สร้าง ซึ่ง **อนุมานได้จากตรรกะล้วน ไม่ต้องพึ่งข้อมูลที่บันทึกไว้**

### ⭐ ตารางนี้จะมีค่าจริงก็ต่อเมื่อ...

...มี `portfolio_id` **เดิมที่ไม่เป็น NULL ปะปนอยู่ก่อน Backfill** — เพราะกรณีนั้น
การกู้คืนต้องรู้ว่า "แถวไหนเคยผูกกับพอร์ตไหน" ซึ่งเดาจากตรรกะไม่ได้

**เคสนี้ไม่มีเลยแม้แต่แถวเดียว** (ยืนยันจาก `portfolios = 0` ก่อน Apply)

> ⚠️ **บทเรียนสำหรับ Migration ชุดถัดไป:** การสร้างตาราง Backup ก่อน Backfill
> ยังเป็นสิ่งที่ควรทำเสมอ — **เหตุผลที่รอบนี้ลบได้ไม่ใช่ "Backup ไม่จำเป็น"
> แต่เป็น "สภาพข้อมูลก่อนหน้าบังเอิญ reconstruct ได้"** ซึ่งเป็นเงื่อนไขเฉพาะของ
> `044` ที่ต้อง **ตรวจก่อนทุกครั้ง** ไม่ใช่สมมติว่าเป็นแบบนี้เสมอ
>
> คำถามที่ต้องถามก่อนลบ Backup ของ Backfill ใดๆ:
> **"ถ้าต้องกู้คืน มีข้อมูลไหนที่อนุมานจากตรรกะไม่ได้บ้าง?"**
> ถ้าคำตอบคือ "ไม่มี" → ลบได้ · ถ้ามีแม้แต่ Field เดียว → **เก็บไว้**

## [Decided] - 27 สิงหาคม 2569 (รอบ 3) — PDPA: ล้างชื่อ `portfolios` / `brokers` ตอน Erasure

**คำถามที่ตั้งต้น:** `portfolios.name` และ `brokers.name` เป็นข้อความที่ผู้ใช้พิมพ์เอง
จึงอาจมี PII จริง (เช่น *"พอร์ตของสมชาย"*) แต่เดิม `userErasure` ไม่แตะทั้งสองตาราง
โดยอ้างเกราะ **Immutable Ledger** เดียวกับ `transactions`

**มติ Founder: ให้ล้างชื่อทั้งสองตาราง**

### เหตุผล — เกราะ Immutable Ledger ไม่ครอบสองตัวนี้

สองตารางนี้เป็น **ป้ายกำกับ ไม่ใช่ตัวเลข** — **ลบชื่อทิ้งแล้วตัวเลขทุกตัวในระบบ
ยังเท่าเดิมเป๊ะ** ต่างจาก `transactions` ที่ลบแล้วยอดเปลี่ยนทันที
เกราะที่ปกป้อง Ledger จึงไม่มีเหตุผลรองรับให้ครอบมาถึงชื่อพอร์ต/โบรก

### ⚠️ วิธีที่ถูก: Anonymize ไม่ใช่ DELETE

ลบแถวจะทำให้ `assets.portfolio_id` / `broker_id` กลายเป็น `NULL`
(FK `ON DELETE SET NULL`) = **แก้ข้อมูลการลงทุนของผู้ใช้** และในกรณีพอร์ตยัง
**ละเมิด Invariant ของ migration 044/045** โดยตรง (สินทรัพย์ทุกแถวต้องสังกัดพอร์ต)

→ เปลี่ยนชื่อเป็นค่ากลางแทน · โครงสร้างอยู่ครบ · Ledger ไม่ถูกแตะแม้แถวเดียว
(Pattern เดียวกับที่ `userRepository.anonymize` ทำกับ `users` อยู่แล้ว)

### 🔴 กับดักที่เกือบทำให้ Erasure ล้มทั้งก้อน

`brokers` มี **`uniq_brokers_user_name_ci ON (user_id, lower(name))`** (migration 042)

ถ้าเปลี่ยนชื่อโบรกทุกตัวเป็นค่าเดียวกัน (เช่น `"โบรก"`) ผู้ใช้ที่มี 3 โบรกจะ
**ชน UNIQUE → Erasure ล้มทั้ง Transaction** และคนที่ยื่นคำขอลบข้อมูลตาม PDPA
**จะลบไม่ได้เลย**

→ ต่อท้ายชื่อด้วย **8 ตัวแรกของ `id`** (Hex ไม่ซ้ำแน่นอน และไม่ใช่ PII)
→ มีเทสต์ที่จำลอง **ผู้ใช้ที่มี 3 พอร์ต + 3 โบรก** โดยเฉพาะ (ผู้ใช้ที่มีอันเดียว
จับกับดักนี้ไม่ได้เลย)

> ตรวจ Schema จริงแล้ว: **`portfolios` ไม่มี UNIQUE บนชื่อ** (มีแค่
> `idx_portfolios_one_default_per_user` ซึ่งเป็น Partial UNIQUE บน `user_id`
> เฉพาะแถว `is_default`) — แต่ยังใส่ตัวแยกเหมือนกันเพื่อกันไว้เผื่อวันหนึ่งมีคนเพิ่ม

### ⚠️ ไม่ Error-Isolated โดยเจตนา

ต่างจากการลบรูปสลิป (ที่ Fail แล้วไปต่อได้) — ถ้าล้างชื่อไม่สำเร็จแล้วเราเดินหน้า
Anonymize `users` ต่อ ผู้ใช้จะถูกบอกว่า **"ลบข้อมูลแล้ว" ทั้งที่ชื่อที่อาจมี PII
ยังอยู่ครบใน DB** = คำตอบที่ผิดต่อคำขอตามกฎหมาย
→ ปล่อยให้ `throw` แล้ว Retry ทั้ง Flow ได้ ดีกว่ารายงานผลลวง

### เหตุผลข้อ 1 — การล็อกต้องหมายถึง "โตต่อไม่ได้" ไม่ใช่ "ออกไม่ได้"

ถ้าบล็อกการขายด้วย ผู้ใช้ที่ขายหุ้นจริงไปแล้วในโลกจริงจะบันทึกไม่ได้ →
**พอร์ตโชว์ตัวเลขผิดถาวร** ("ยังถือ BTC 0.5 อยู่" ทั้งที่ขายไปแล้ว) และกำไร/ขาดทุน
ที่เขาเห็นจะผิดตลอดไป ซึ่ง:

- ขัดกับจุดยืนทั้งหมดของผลิตภัณฑ์ (บันทึกให้ตรงความจริง)
- เท่ากับ **"เอาข้อมูลผู้ใช้เป็นตัวประกันค่าสมาชิก"** ซึ่งอยู่คนละเรื่องกับการจำกัดฟีเจอร์
  และขัดกับ Non-Goal ใน `AI_CONTEXT.md` ("ไม่บังคับซื้อ Premium เพื่อเข้าถึงข้อมูล
  ที่เคยบันทึกไว้แล้ว")

**กฎการเลือกพอร์ตที่ตรวจ: ตรวจ "ปลายทางของของใหม่" เสมอ ไม่ใช่ต้นทาง** — กฎข้อเดียว
นี้ให้ผลถูกทุกเคสพร้อมกัน (ย้ายออก → ปลายทางคือพอร์ตหลักซึ่งเขียนได้ → ผ่าน ·
ย้ายเข้า/ซื้อเข้าพอร์ตส่วนเกิน → ปลายทางถูกล็อก → บล็อก)

> ⚠️ **ข้อความที่ผู้ใช้เห็นต้องบอกทางออกที่ยังทำได้จริงให้ครบ** — คำว่า
> "พอร์ตนี้อ่านได้อย่างเดียว" ลอยๆ ชวนให้เข้าใจว่าทำอะไรไม่ได้เลย แล้วผู้ใช้จะ
> **ไม่บันทึกการขายที่เกิดขึ้นจริง** ทำให้ยอดผิดถาวร ซึ่งเป็นสิ่งที่มติข้อนี้
> ตั้งใจกันตั้งแต่แรก · และห้ามใช้ภาษาชี้นำการลงทุน (กฎเหล็กข้อ 1)

### เหตุผลข้อ 2 — `created_at` เก่าสุดมักไม่ใช่พอร์ตที่ผู้ใช้ใช้จริง

พอร์ตที่ `created_at` เก่าสุดคือตัวที่ **migration 044 Backfill สร้างให้อัตโนมัติ**
(ชื่อ Default ชนิด `'custom'` ซึ่งอาจแทบว่างเปล่า) ส่วนพอร์ตที่ผู้ใช้ใช้จริงคือตัวที่
เขาสร้างเองทีหลัง → ยึด `created_at` จะ **ล็อกผิดตัว**: ผู้ใช้เขียนพอร์ตหลักของตัวเอง
ไม่ได้ ทั้งที่เขียนพอร์ตร้างได้

`is_default` คือ "พอร์ตหลักของผู้ใช้" ตามความหมายอยู่แล้ว · DB การันตีว่ามีได้ 1 อัน
ต่อ user เป๊ะ (`idx_portfolios_one_default_per_user`) · และ **ผู้ใช้เปลี่ยนเองได้**
ผ่าน `PATCH /portfolios/{id}` `{ isDefault: true }` จึงไม่ถูกขังอยู่กับพอร์ตที่ระบบ
เลือกให้

> ⚠️ **Fallback (`created_at` + tie-break `id`) ห้ามลบทิ้ง** — ใช้เมื่อ `is_default`
> หายไป (Invariant ของ 044/045 พัง) ถ้าไม่มี Fallback ฟังก์ชันจะคืน Set ว่าง =
> **ล็อกผู้ใช้ออกจากทุกพอร์ตพร้อมกัน** ซึ่งแย่กว่าการเลือกผิดตัวมาก

|---|---|---|
| — | แถว `dividend` เก็บ `quantity`/`price_per_unit` ยังไง (Schema บังคับ > 0 แต่ Doc บอก optional) | **บังคับผู้ใช้กรอกจำนวนหน่วยที่ได้ปันผล** แล้วคำนวณ `price_per_unit = amount_thb / quantity` (= **บาทต่อหุ้น / DPS**) · **ไม่ผ่อน CHECK ของตารางเงิน** ด้วยเหตุผลเดียวกับที่ Design Doc § 5.3 ให้ไว้เองตอนอธิบายว่าทำไมไม่ใช้ `amount` ติดลบ (ผ่อนเกราะเพื่อ type เดียว = เปิดช่องให้บั๊กของ `buy`/`sell` ทะลุถึง DB ด้วย) · ค่าที่ได้ไม่ใช่ค่าขยะเพื่อให้ผ่าน Constraint แต่ตรงกับหน้าตาสลิปปันผลไทยจริง ("0.50 บาท/หุ้น × 1,000 หุ้น = 500 บาท") |

**เหตุผลที่ "ไม่เติมยอดถือให้เอง" ทั้งที่ระบบคำนวณได้:**

`heldQuantityAsOf()` คำนวณยอดถือ ณ วันที่ได้ปันผลได้อยู่แล้ว การเอามาเติมให้เมื่อ
ผู้ใช้ไม่กรอกจึงดู "สะดวกกว่า" — แต่ขัด **กฎยืนข้อ 11** ("Silent Default เป็น
Anti-pattern เสมอ — พาร์สข้อมูลไม่ชัดเจนต้องถามผู้ใช้หรือ Reject ไม่ใช่เดาค่า Default")

จำนวนหน่วยที่ *ระบบรู้* กับที่ *ได้ปันผลจริง* **ไม่จำเป็นต้องเท่ากันเลย**:
- ปันผลจ่ายตามยอด ณ **วัน XD** ซึ่งมักเป็นคนละวันกับวันที่เงินเข้าบัญชี
- ผู้ใช้จำนวนมากเพิ่งเริ่มบันทึกกลางทาง ระบบจึงเห็นประวัติไม่ครบตั้งแต่ต้น

และค่านี้ไม่ได้จบในตัวเอง — มันไหลต่อไปเป็น `price_per_unit` (DPS) ที่ผู้ใช้เอาไป
**เทียบข้ามงวดจริง** การเดาแทนผู้ใช้จึงเท่ากับเขียนตัวเลขที่ไม่มีใครยืนยันลง
Immutable Ledger ถาวร แล้วผิดแบบเงียบสนิท

> ⚠️ **`heldQuantityAsOf` ห้ามถูกลบทิ้ง** — ยังทำหน้าที่เป็นด่าน
> `NOTHING_TO_RECEIVE_DIVIDEND` ซึ่งตรวจจาก **ยอดถือจริง ณ `date` เสมอ ไม่ใช่จาก
> `quantity` ที่ผู้ใช้กรอก** (ไม่งั้นผู้ใช้กรอกตัวเลขอะไรก็ได้ก็ข้ามด่านได้ =
> บันทึกปันผลของหุ้นที่ไม่เคยถือ) · `quantity` = "สิ่งที่ผู้ใช้อ้าง" ·
> `heldQuantityAsOf` = "ของจริงที่ระบบยืนยันได้" — คนละบทบาท ต้องมีทั้งคู่

**หมายเหตุลำดับเวลา:** commit `a9f8f3d` (Stage 6b) ทำเป็น optional ไว้ก่อน เพราะเขียน
ขึ้น *ก่อน* มติข้อนี้จะมาถึง ไม่ใช่การจงใจขัดมติ — แก้ตามในคอมมิตถัดมา
