## 1. Summary

รอบนี้ปิด **2 บั๊คคนละตัว** ที่มีอาการเหมือนกัน — ตัวเลขที่ผู้ใช้เห็นบนหน้าจอไม่ตรงกับ
ตัวเลขที่ระบบบันทึกลง Ledger จริง

| | บั๊ค A | บั๊ค B |
|---|---|---|
| อาการ | Preview 100 บาท → บันทึก 100.01 บาท | สลิประบุมูลค่าหุ้น 106.44 → ระบบใช้ 106.32 และแสดง "รวมจ่ายจริง 106.59" ทั้งที่จ่ายจริง 106.72 |
| ต้นตอ | เศษที่ถูกปัดทิ้งตอนหาร `quantity` ถูกคูณราคากลับขึ้นมา | `resolveGrossAmount` ตรวจสอบไม่ได้เพราะ AI อ่าน `net_amount` ไม่ได้ |
| ทางเข้าที่พบ | **3 ทาง** (LINE Confirm · Postback สลิป · ฟอร์มเว็บ) | 1 ทาง (แต่กระทบทั้งการ์ด LINE และฟอร์มเว็บ) |
| Commit | `1d2bf50`, `cbb375a` | `a42c4a4` |

ทั้งคู่แก้ด้วยหลักการเดียวกันตามมติ Founder: **ยอดที่บันทึกลง Ledger ต้องเท่ากับยอดที่
ผู้ใช้เห็นตอนกดยืนยันเสมอ** ตัวเงิน 1 สตางค์ไม่ใช่ประเด็น ประเด็นคือแอปการเงินที่แสดง
เลขหนึ่งแล้วบันทึกอีกเลขหนึ่งทำลายความเชื่อใจ

## 3. Root cause

### 3.1 บั๊ค A — เศษจากการปัด `quantity` ถูกคูณกลับขึ้นมา

`transaction.service.resolveQuantityAndPrice` มี Branch แยกตามรูปแบบ Input:

```
Branch 1: isPresent(quantity) && isPresent(pricePerUnit)  → amountThb = roundToTwo(quantity × pricePerUnit)
Branch 3: isPresent(amountThb)                            → quantity  = deriveQuantityFromAmount(amountThb, price)
```

**ตอน Preview** คำสั่ง `ซื้อ BTC 100` เข้า Branch 3:
- `amountThb = roundToTwo(100) = 100` ← ยอดที่ผู้ใช้เห็นและตกลงด้วย
- `quantity = roundToEight(100 / 2513380) = 0.00003979` ← **ปัดทิ้งเศษไป**

`pending_transactions` เก็บครบทั้ง `quantity` + `price_per_unit` + `amount_thb`

**ตอน Confirm** `pendingTransaction.service.toCommitParams` ส่งต่อแค่ `quantity` และ
`pricePerUnit` — **ไม่ส่ง `amountThb`** ที่ Snapshot ไว้ ทำให้เข้า Branch 1 แทน แล้ว
**คำนวณยอดขึ้นมาใหม่**:

```
0.00003979 × 2,513,380 = 100.0073…  → roundToTwo → 100.01
```

เศษที่หายไปตอนปัด `quantity` เหลือ 8 ตำแหน่ง (ตาม `NUMERIC(20,8)`) ถูกคูณราคากลับ
ขึ้นมาเป็น 1 สตางค์ ขอบเขตความคลาดเคลื่อน = `0.5e-8 × pricePerUnit` — ยิ่งราคาต่อหน่วย
สูงยิ่งโผล่ชัด (BTC ที่ 2.5 ล้าน → คลาดได้ถึง ~0.0126 บาท)

**ทางเข้าที่ 2** — Postback สลิปทาง LINE (`webhook.controller` case `ocr_confirm`) พก
แค่ `qty` + `price` เช่นกัน กลไกเดียวกันเป๊ะ

**ทางเข้าที่ 3** — `transactions.controller` Branch `hasPrice` (ฟอร์มเว็บกรอกจำนวนเงิน
\+ ราคาเอง) หาร `deriveQuantityFromAmount` แล้วให้ Service คูณกลับ กลไกเดียวกันเป๊ะ
Comment เดิมในโค้ดยอมรับความคลาดเคลื่อนนี้ไว้เองแล้วสรุปว่ารับได้เพราะ *"หุ้นไทยราคา
หลักพัน ผลคูณจึงต่ำกว่า 0.005 เสมอ"* — **ข้อสรุปนั้นผิด** เพราะ Branch นี้เปิดให้กรอก
ราคาเองได้ทุกสินทรัพย์ (Guard บังคับเฉพาะหุ้นไทย แต่ *อนุญาต* ทุกตัว)

### 3.2 บั๊ค B — `resolveGrossAmount` ไม่มีข้อมูลให้ตรวจสอบ

`slipOcr.service.resolveGrossAmount` ตัดสินว่าจะเชื่อ "มูลค่าหุ้น" ที่ AI อ่านมาหรือไม่
โดยใช้ค่าธรรมเนียมเป็นตัวพิสูจน์ (ซื้อ: `net = gross + fee` / ขาย: `net = gross − fee`)
Logic เดิมมี 3 กฎ แต่ **ทุกกฎต้องมี `netAmount` ก่อน**:

```js
if (net === null || fee === null) {
  return { amount: computed, source: 'computed', reason: 'no_fee_or_net_to_verify' };
}
```

Production Log (Railway service `EasyDCA`, 22 ส.ค. 2569) — ค่าดิบ:

```
14:21:03 ASTS source="computed" reason="no_fee_or_net_to_verify" aiAmount=1497.6 netAmount=null feeTotal=2.4  resolvedAmount=1497.58
14:22:01 EOSE source="computed" reason="no_fee_or_net_to_verify" aiAmount=106.44 netAmount=null feeTotal=0.27 resolvedAmount=106.32
```

**AI อ่านมูลค่าหุ้น (106.44) และค่าธรรมเนียม (0.27) ถูกต้องทั้งคู่ แต่ตอบ
`net_amount = null` ทุกใบ** → หลุด Guard บรรทัดแรกทันที Rule 2 (ที่ควรจับเคสนี้ได้)
จึงไม่เคยมีโอกาสทำงานเลยแม้แต่ครั้งเดียว

สาเหตุที่ AI อ่าน `net_amount` ไม่ได้: `SYSTEM_PROMPT` ยกตัวอย่างป้ายกำกับแบบ Settrade
(*"ยอดที่จะได้รับคืนโดยประมาณ"* / *"ยอดชำระทั้งสิ้น"*) แต่สลิป Dime! แสดงยอดรวมเป็น
**ตัวเลขขนาดใหญ่บนสุดของสลิปโดยไม่มีป้ายกำกับ** Model จึงไม่จัดว่ามันคือยอดสุทธิ

### 3.3 บั๊ค B ชั้นที่สอง — ฟอร์มเว็บไม่เคยใช้ค่าจาก Backend เลย

`DcaForm.jsx:941` คำนวณ `gross = q × p` เองในเบราว์เซอร์ **ไม่เคยอ่าน `amountTotal`
ที่ Backend ส่งมา** บังเอิญได้เลขเดียวกัน (106.32) จึงแยกไม่ออกจากหน้าจอ

**ถ้าแก้แต่ `resolveGrossAmount` อาการที่ Founder เห็นจะไม่หายเลยแม้แต่นิดเดียว** —
จุดนี้ Log ตอบไม่ได้ ต้องไล่โค้ดเท่านั้นถึงเจอ

## 4. Why it produced the symptom

**บั๊ค A:** ผู้ใช้เห็นการ์ด Preview ที่สร้างจาก `pending` record (ยอด 100 ที่ Snapshot
ไว้) แต่การ์ดยืนยันสร้างจากผลลัพธ์ของ `processBuyCommand` ซึ่งคำนวณยอดขึ้นใหม่ —
**สองการ์ดอ่านยอดจากคนละแหล่ง** ทั้งที่ผู้ใช้เข้าใจว่าเป็นรายการเดียวกัน

**บั๊ค B:** บรรทัด "รวมจ่ายจริง" ในทั้ง `flexMessage.util` และ `DcaForm.jsx` เขียนว่า
`netAmount ?? (gross + fee)` — เมื่อ `netAmount` เป็น null ระบบ**บวกเอง**แล้ว**แปะป้าย
ว่าเป็นยอดที่จ่ายจริง** ผลคือ `106.32 + 0.27 = 106.59` ถูกนำเสนอเป็นข้อเท็จจริง ทั้งที่
เป็นค่าที่ระบบเดาเอง และผิดจริง (จ่ายจริง 106.72)

นี่ไม่ใช่ "ตัวเลขคลาดเคลื่อน" แต่เป็น **ข้อความที่ผิดข้อเท็จจริง** — ผู้ใช้ไม่มีทางรู้ว่า
เลขไหนเชื่อได้เลขไหนเดา

## 5. Fix

### บั๊ค A — `1d2bf50` + `cbb375a`

1. `pendingTransaction.toCommitParams` พก `amountThb` ที่ Snapshot ไว้ต่อไปด้วย
2. `resolveQuantityAndPrice` Branch 1 ใช้ยอดที่ตกลงไว้เมื่อได้รับมา — **ยังคำนวณจาก
   `quantity × pricePerUnit` เหมือนเดิมทุกประการเมื่อไม่ได้รับ** (เส้นทาง "พิมพ์จำนวน
   หน่วย + ราคาเอง" ซึ่งไม่เคยมียอดตกลงไว้ก่อน จึงต้องไม่เปลี่ยน)
3. `resolveAgreedAmount` — Guard 2% + `console.warn` ทุกครั้งที่ปฏิเสธ

   **ทำไมต้องมี Guard:** นี่คือทางเข้า Immutable Ledger ที่รับค่าจาก Postback ซึ่งผู้ใช้
   แก้ได้ ยอมรับดิบๆ ไม่ได้ · ใช้ 2% ให้ตรงกับ `SANITY_RATIO` ของ `slipOcr.service` ที่
   ตอบคำถามเดียวกันเป๊ะ ("ยอดนี้เข้าคู่กับ quantity × price ไหม") · Fail-safe = กลับไป
   คำนวณเอง (พฤติกรรมเดิม) ไม่ใช่ค่าที่เชื่อไม่ได้
4. `validateSell` เส้นทาง `sellAll` **ตัด `amountThb` ที่อาจติดมากับ `params` ทิ้งเสมอ**
   — เส้นทางนี้คำนวณทั้ง `quantity` (ยอดคงเหลือ ณ ตอนนี้) และราคา (ราคาตลาด ณ ตอนนี้)
   ขึ้นใหม่ทั้งคู่ ยอดที่ตกลงไว้ก่อนหน้าจึงไม่ใช่ยอดของคู่นี้
5. `transactions.controller` Branch `hasPrice` ส่ง `params.amountThb = amountTotal`

### บั๊ค B — `a42c4a4`

1. **Prompt** — เพิ่มคำอธิบายว่ายอดรวมของแอปหุ้นต่างประเทศ (Dime!) อยู่ตรงไหนบนสลิป
   (ตัวเลขใหญ่บนสุด ไม่มีป้ายกำกับ) คงโมเดล `claude-sonnet-5` เดิมตามข้อบังคับ

   ⚠️ **จุดที่เกือบพลาด:** Draft แรกเขียนใบ้ไว้ว่า *"สังเกตว่ามันมักมากกว่า amount
   อยู่เท่ากับค่าธรรมเนียมพอดีเมื่อเป็นการซื้อ"* — **ถอดออกก่อน Commit** เพราะเป็นการ
   ชวนให้ AI คำนวณ `net = amount + fee` เอง ถ้า AI ทำแบบนั้น `derived = net − fee`
   จะเท่ากับ `ai` เสมอ → Rule 2 ผ่านทุกครั้งแบบวงกลม → **ช่องโหว่ BCPG เปิดกลับทันที**
   ข้อความที่เหลือย้ำกฎเดิมให้เข้มขึ้นแทน ("ห้ามบวก/ลบ amount กับค่าธรรมเนียมเอง")

2. **ทางสำรอง Deterministic เมื่อ `net` เป็น null** — แยกสองความเป็นไปได้ด้วยลายเซ็น
   เชิงตัวเลข โดยไม่ต้องเชื่อ AI:

   | สมมติฐาน | ลายเซ็น | การตัดสิน |
   |---|---|---|
   | AI หยิบยอดสุทธิมาผิดช่อง (BCPG) | `ai ≈ computed ∓ fee` **พอดี** | VETO — ไม่เชื่อ ใช้ค่าคำนวณ |
   | `ai` คือมูลค่าหุ้นจริง | ต่างจาก `computed` เท่าที่การปัดราคาอธิบายได้ | ยอมรับ |

   ขอบเขต = `priceRoundingDrift(quantity, pricePerUnit)` = `|qty| × 0.5 × 10^(−decimals) + 0.01`
   โดยบังคับ `decimals ≥ 2` (`MIN_PRICE_DECIMALS`) — **จำเป็น** เพราะจำนวนทศนิยมนับจาก
   ตัวเลขที่ `JSON.parse` ให้มา ราคาที่พิมพ์ว่า `100.00` จะกลายเป็น `100` (0 ตำแหน่ง)
   ทำให้ช่องยอมรับกว้างขึ้น 100 เท่าโดยไม่มีเหตุผลรองรับ · มี `SANITY_RATIO` 2% ซ้อนอีกชั้น

   ตรวจกับเคสจริงทั้ง 3: EOSE ยอมรับ 106.44 (ต่าง 0.12 ≤ 0.135) · ASTS ยอมรับ 1497.60
   (ต่าง 0.02 ≤ 0.11) · BCPG VETO ยิงก่อน (`69.00 − 0.11 = 68.89` = `ai` เป๊ะ)

3. **บรรทัด "รวมจ่ายจริง" ต้องไม่โกหก** — ทั้ง `flexMessage.util` และ `DcaForm.jsx`:
   สลิประบุยอดสุทธิ → แสดงตามสลิป ป้าย "รวมจ่ายจริง/รับจริง" ได้เต็มปาก · สลิปไม่ระบุ →
   เปลี่ยนป้ายเป็น **"รวมโดยประมาณ"** + ข้อความกำกับว่าระบบคำนวณเอง

4. **เลขที่แสดง = เลขที่บันทึก** (ไม่งั้นการ์ดจะโชว์ 106.44 แต่ Ledger ได้ 106.32 =
   บั๊ค A ซ้ำรอยบนเส้นทางสลิป): LINE พก `gross` ไปกับ Postback ปุ่มยืนยันเมื่อ
   `amountSource='slip_gross'` · เว็บส่ง `amountTotal` คู่กับ `quantity + pricePerUnit`
   ตราบใดที่ผู้ใช้ยังไม่แก้ช่องจำนวน/ราคา — **ทั้งสองทางผ่าน `resolveAgreedAmount` เสมอ**

5. **Log ยิงทุกครั้งที่อ่านสลิป** (เดิมยิงเฉพาะตอน `source !== 'slip_gross'`) — Log เดิม
   พอวินิจฉัยบั๊คได้ แต่ทำให้ "ยืนยันหลังแก้ว่าใช้เลขจากสลิปได้แล้วจริง" ไม่มีร่องรอยให้ดู

## 6. How it was found

ทำตาม `debug-mantra` 4 ขั้น — **ขั้นที่ 3 (หาทางหักล้างสมมติฐานก่อน) คือขั้นที่ให้ผลจริง**

| # | สมมติฐาน | ผล |
|---|---|---|
| H1 | Rule 2 ของ `resolveGrossAmount` มีบั๊คในตรรกะ (สมมติฐานตั้งต้นใน Brief) | **หักล้าง** — ถ้าจริง Log ต้องขึ้น `reason=ai_amount_inconsistent_with_net_and_fee` พร้อม `netAmount` ที่ไม่ใช่ null แต่ Log จริงขึ้น `no_fee_or_net_to_verify` + `netAmount=null` |
| H2 | `SLIP_ROUNDING_TOLERANCE` (0.02) แคบไป | **หักล้าง** — Tolerance ไม่เคยถูกใช้เลย เพราะหลุด Guard บรรทัดแรกไปก่อน |
| H3 | AI อ่าน `net_amount` ไม่ได้ | **ยืนยัน** — Log ตรงทั้ง 2 ใบ (EOSE + ASTS) |
| H4 | ฟอร์มเว็บแสดง 106.32 เพราะรับค่ามาจาก `resolveGrossAmount` | **หักล้าง** — `DcaForm.jsx:941` คำนวณ `q × p` เองในเบราว์เซอร์ ไม่เคยอ่านค่าจาก OCR (บังเอิญได้เลขเดียวกัน) |

**เครื่องมือที่ใช้:** `railway logs --service EasyDCA | grep "slip ocr gross"` (Log ที่โค้ด
มีอยู่แล้วจากบทเรียนเคส BCPG) — ตอบทั้ง `source`/`reason`/`netAmount`/`feeTotal`/`aiAmount`
ได้ครบในบรรทัดเดียว **ไม่ต้องดาวน์โหลดรูปมา Replay ผ่าน Claude ใหม่เลย**

**การทบทวนขั้นสุดท้าย (`scrutinize`) จับเพิ่มได้ 2 จุดที่ดู Diff อย่างเดียวมองไม่เห็น:**
- การ์ด LINE จะแสดง 106.44 แต่ Postback พกแค่ `qty`+`price` → Ledger ได้ 106.32
  (เท่ากับสร้างบั๊ค A ตัวใหม่ขึ้นมาเองระหว่างแก้บั๊ค B)

## 10. บทเรียนที่เอาไปใช้ต่อได้

1. **Mock ที่รอยต่อ = จุดบอดที่มองไม่เห็นจากทั้งสองฝั่ง** — เทสต์ทั้งสองไฟล์เขียวสนิท
   ตลอดเวลาที่บั๊คมีอยู่จริง เพราะต่างฝ่ายต่าง Mock อีกฝ่ายทิ้ง งานที่แตะ 2 Service
   ต่อกันควรมีเทสต์ที่ใช้ของจริงทั้งคู่อย่างน้อย 1 ตัว
2. **Comment ที่ยอมรับข้อจำกัดไว้เอง = บั๊คที่รอเวลา** — ถ้าเขียนได้ว่า "อาจคลาดได้ใน
   กรณี X" แต่ไม่มี Guard/Test บังคับ ข้อสมมตินั้นจะพังเงียบๆ วันที่ขอบเขตขยาย
3. **ระวังการแก้ Prompt ที่ทำให้ตัวตรวจสอบกลายเป็นวงกลม** — การบอก AI ว่า "ค่า A มัก
   เท่ากับ B บวก C" ทำให้ AI เดา A จาก B+C แล้วสมการที่เราใช้ตรวจก็จะผ่านเสมอโดยไม่ได้
   ตรวจอะไรเลย
4. **Log ที่ยิงเฉพาะตอนผิด ตอบไม่ได้ว่าตอนถูกมันถูกจริงไหม** — Log เดิมช่วยวินิจฉัยได้ดีมาก
   แต่พอแก้เสร็จกลับไม่มีร่องรอยยืนยันผล ต้องกลับมาแก้ Log เพิ่มอีกรอบ
5. **แก้ Backend อย่างเดียวไม่พอเมื่อ Frontend คำนวณเองซ้ำ** — ค่าที่ผ่านการตรวจสอบมา
   อย่างดีไม่มีความหมายถ้าหน้าจอไม่ได้ใช้มัน ต้องไล่ให้ถึงพิกเซลที่ผู้ใช้เห็นจริง
