## 1. Summary

หลัง Deploy โค้ดใหม่ (`a05206d`) และ Apply `migration 042 → 045` เสร็จ
**ทุกคำสั่งซื้อผ่าน LINE พังทันที** ด้วย Error:

```
Failed to create pending transaction:
Could not find the 'broker_id' column of 'pending_transactions' in the schema cache
```

สาเหตุคือ **โค้ดที่ Deploy ไปแล้วต้องการคอลัมน์ที่ยังไม่ได้ Apply** —
`pending_transactions.broker_id` ถูกเพิ่มโดย **`migration 046`** ซึ่งตามลำดับที่
วางไว้ใน `HANDOFF § 8` อยู่ที่ **ขั้นสุดท้าย (ขั้น 8)**

**ความรุนแรง:** 🟠 พังแบบ **ดัง** (ผู้ใช้เห็น Error ทันที) · **ไม่แตะ Ledger เลย** ·
**ไม่มีข้อมูลเสียหายแม้แต่แถวเดียว**

**เวลาที่ใช้แก้:** ทันทีที่วินิจฉัยได้ — Apply `046` + `NOTIFY pgrst, 'reload schema';`

## 3. Root Cause

### 3.1 ลำดับที่วางไว้ตอบคำถามแค่ทิศเดียว

`HANDOFF § 8` วิเคราะห์ไว้อย่างละเอียดว่า **`044` ทำให้โค้ดเดิมพัง** (Backfill แล้ว
`.is('portfolio_id', null)` หาไม่เจอ) จึงสรุปว่าต้อง **Deploy โค้ดใหม่ก่อน** แล้วค่อย
Apply — ซึ่ง **ถูกต้องสำหรับ `044`**

แต่ไม่มีใครถามคำถามตรงข้าม: **"โค้ดใหม่ที่กำลังจะ Deploy ต้องการอะไรจาก Schema บ้าง"**

คำตอบอยู่ในโค้ดชัดเจนมาตั้งแต่ Stage 5:

```js
// pendingTransaction.service.createPending → pendingRepository.create({...})
broker_id: data.brokerId ?? null,   // ← คอลัมน์นี้มาจาก migration 046
```

**ทุกครั้ง** ที่สร้าง Pending โค้ดจะเขียนคอลัมน์นี้ ไม่ว่าผู้ใช้จะระบุโบรกหรือไม่
— ไม่ใช่ Path ที่เกิดขึ้นเป็นบางกรณี

### 3.2 สองทิศชนกันจริง — ไม่มีลำดับไหนที่ไม่พังเลย

| Migration | ทิศของแรงบังคับ | ผลต่อลำดับ |
|---|---|---|
| `044` | ทำให้ **โค้ดเดิม** พัง | ต้อง **Deploy โค้ดใหม่ก่อน** Apply |
| `046` | **โค้ดใหม่** ต้องการคอลัมน์จากมัน | ต้อง **Apply ก่อน** Deploy โค้ดใหม่ |

**ข้อบังคับสองข้อนี้ขัดกันโดยตรง** → ไม่ว่าจะเรียงยังไงก็ต้องมีช่วงที่ระบบพัง
คำถามที่แท้จริงจึงไม่ใช่ *"จะเรียงยังไงให้ไม่พัง"* แต่คือ
**"จะให้พังตอนไหน นานแค่ไหน และเตรียมรับมือยังไง"**

ลำดับที่ใช้จริงเลือกคำตอบที่แย่ที่สุดโดยไม่ตั้งใจ: วาง `046` ไว้ **ขั้นสุดท้าย**
ทำให้ช่วงพังยาวที่สุดเท่าที่เป็นไปได้

### 3.3 PostgREST Schema Cache ทำให้ดูเหมือนยังพังอยู่หลังแก้

หลัง Apply `046` แล้ว Error **ยังไม่หายทันที** เพราะ PostgREST cache Schema ไว้
ต้องสั่ง `NOTIFY pgrst, 'reload schema';` เอง — ถ้าไม่รู้ข้อนี้จะเข้าใจผิดว่า
Migration ไม่ได้ผลแล้วไปแก้ผิดจุด

## 4. ⭐ ทำไมเทสต์ 137 suites / 2,728 ตัว จับไม่ได้เลย — และ **จะจับไม่ได้ตลอดไป**

> **ข้อนี้สำคัญกว่าตัวบั๊ก** เพราะข้อสรุปคือ "อย่าพยายามแก้ด้วยเทสต์"

เทสต์ทุกตัวในโปรเจกต์ **Mock Repository** (`jest.mock('../src/repositories/...')`)
ซึ่งแปลว่า **ไม่มีเทสต์ตัวไหนแตะ Schema จริงเลยแม้แต่ตัวเดียว** —
`pendingRepository.create({ broker_id: ... })` ถูกแทนที่ด้วย `jest.fn()` ที่รับ
Argument อะไรก็ได้โดยไม่สนใจว่าคอลัมน์นั้นมีอยู่จริงหรือไม่

### ❌ วิธีที่ **ไม่** ได้ผล (และห้ามเสนอ)

| ข้อเสนอที่ดูสมเหตุสมผล | ทำไมถึงกันไม่ได้จริง |
|---|---|
| "เขียนเทสต์เช็คว่าคอลัมน์มีอยู่" | เทสต์รันกับ Mock ไม่ได้รันกับ Supabase จริง — เช็คได้แค่ว่า Mock มีคอลัมน์ ซึ่งเราเป็นคนเขียน Mock เอง |
| "เพิ่ม Integration Test ที่ต่อ DB จริง" | ต้องมี Postgres ใน CI + ต้อง Apply migration ตามลำดับจริง = สร้างระบบใหม่ทั้งชุด และ**ยังไม่กันเคสนี้อยู่ดี** เพราะปัญหาคือ *ลำดับตอน Deploy จริง* ไม่ใช่ *โค้ดผิด* |
| "ให้ `045` ตรวจว่า `046` Apply แล้วหรือยัง" | ผิดลำดับตรรกะ — `045` รันก่อน `046` โดยการออกแบบ |

> ### ⚠️ การเสนอวิธีที่กันไม่ได้จริง = สร้างความมั่นใจปลอมๆ ซึ่งอันตรายกว่าไม่มีอะไรเลย
>
> ถ้าเขียนเทสต์ที่ "ดูเหมือนกันเคสนี้" แล้วมันเขียว รอบหน้าจะมีคนเชื่อว่าปลอดภัย
> ทั้งที่ไม่ได้กันอะไรเลย — นี่คือรูปแบบเดียวกับ **"Mock ที่หลวมกว่าของจริง"**
> ที่ทำให้บั๊ก Asset Resolution รอดมาได้ถึง 5 หาง (`AI_WORK_POLICY § 3.1`)

### ✅ สิ่งที่กันได้จริง — **Checklist ตอนวางแผน Deploy** ไม่ใช่เทสต์

เคสนี้เป็นความผิดพลาดของ **กระบวนการวางแผน** ไม่ใช่ของโค้ด จึงต้องกันที่กระบวนการ:

> ### 📋 ก่อนวางลำดับ Deploy/Migration ทุกครั้ง — ตอบให้ครบ **ทั้งสองทิศ**
>
> **ทิศที่ 1 — Migration ทำให้โค้ดเดิมพังไหม?**
> ไล่ดูว่า migration ตัวไหน *เปลี่ยนข้อมูล/โครงสร้างที่โค้ดที่รันอยู่พึ่งพา*
> → ถ้ามี ต้อง **Deploy โค้ดใหม่ก่อน**
>
> **ทิศที่ 2 — โค้ดใหม่ต้องการอะไรจาก Schema ที่ยังไม่มี?**
> `grep` หาคอลัมน์/ฟังก์ชัน/ตารางใหม่ทุกตัวที่ migration ชุดนี้เพิ่ม แล้วเช็คว่า
> **โค้ดที่กำลังจะ Deploy อ้างถึงมันหรือยัง**
> → ถ้ามี ต้อง **Apply migration นั้นก่อน Deploy**
>
> ```bash
> # ตัวอย่างคำสั่งที่ใช้ได้จริงกับเคสนี้ — ใช้เวลาไม่ถึงนาที
> # 1) คอลัมน์/ฟังก์ชันใหม่ทั้งหมดที่ migration ชุดนี้เพิ่ม
> grep -n "ADD COLUMN\|CREATE TABLE\|CREATE OR REPLACE FUNCTION" backend/migrations/04*.sql
>
> # 2) โค้ดที่จะ Deploy อ้างถึงตัวไหนบ้าง (เคสนี้จะเจอ broker_id ทันที)
> grep -rn "broker_id\|portfolio_id" backend/src/repositories/
> ```
>
> **ทิศที่ 3 — สองทิศแรกชนกันไหม?**
> ถ้าชน = **มีช่วงพังแน่นอน ยอมรับตั้งแต่ตอนวางแผน** แล้วเลือกอย่างใดอย่างหนึ่ง:
> 1. **บีบช่วงพังให้สั้นที่สุด** — Apply migration ที่โค้ดใหม่ต้องการให้ **ติดกับ
>    การ Deploy ทันที** ไม่ใช่ทิ้งไว้ท้ายลำดับ (เคสนี้ควรเป็น `046` ก่อน `044` ด้วยซ้ำ)
> 2. **แยก Deploy เป็นสองรอบ** — รอบแรก Deploy เฉพาะโค้ดที่ไม่ต้องการ Schema ใหม่
> 3. **ประกาศ Maintenance ล่วงหน้า** ถ้าช่วงพังยาว
>
> **ทิศที่ 4 — หลัง Apply แล้วต้อง reload อะไรไหม?**
> ⚠️ migration ที่ **เพิ่ม/ลบคอลัมน์** ต้องตามด้วย `NOTIFY pgrst, 'reload schema';`
> เสมอ ไม่งั้น PostgREST จะยังตอบ Error เดิมทั้งที่ Schema ถูกต้องแล้ว

## 5. ⭐ บทเรียนที่ซ้ำรอยเดิม — คำกล่าวอ้างที่ครอบไม่ครบ

`HANDOFF § 8` เขียนไว้ว่า:

> *"...จึง Deploy ก่อนได้อย่างปลอดภัย **และเป็นลำดับเดียวที่ไม่มีช่วงเวลาที่ระบบพัง**"*

**ประโยคนี้ผิด** และผิดด้วยกลไกเดียวกับบทเรียนข้อ 1 ของ
[`POSTMORTEM_PORTFOLIO_RESOLUTION.md`](./POSTMORTEM_PORTFOLIO_RESOLUTION.md):
**วิเคราะห์ครบมิติเดียวแล้วสรุปเหมารวมทั้งหมด**

- วิเคราะห์ `044` อย่างละเอียด → ถูกต้อง
- แล้วสรุปเป็นคำกล่าวอ้างที่ครอบ **migration ทั้งชุด** → ผิด เพราะ `046` คนละมิติกัน

> ### กฎที่ตอกย้ำ (เกิดขึ้นเป็นครั้งที่ 4 ในโปรเจกต์นี้)
>
> คำว่า **"เดียว" / "ไม่มี...เลย" / "เสมอ" / "ทุกจุด"** ในเอกสารและคอมเมนต์
> = ข้อผูกพันที่ต้องพิสูจน์ให้ครบ **ทุกมิติ** ก่อนเขียน
> — ไม่ใช่พิสูจน์มิติที่กำลังคิดถึงอยู่แล้วเหมาว่าครบ
>
> เอกสารที่ผิดแบบนี้ **อันตรายกว่าไม่มีเอกสาร** เพราะคนอ่านรอบหน้าจะใช้มัน
> ตัดสินใจว่า "ตรวจแล้ว ไม่ต้องคิดซ้ำ"
