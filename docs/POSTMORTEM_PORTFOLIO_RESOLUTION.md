## 3. Root Cause

### 3.1 ต้นตอเดียว กระจายด้วย Copy-paste

```js
// assetResolution.service.js:62 (เดิม) — ต้นตอ
async function resolveOwnedAsset(userId, symbol, { portfolioId = null, brokerId } = {}) {
                                                              // ↑ Default นี้คือจุดเริ่ม
```

แล้ว Caller ทุกตัวก็เขียนตามกันหมด:

| ไฟล์ | โค้ดเดิม |
|---|---|
| `transaction.service.js` (validateBuy) | `const portfolioId = params.portfolioId ?? null;` |
| `transaction.service.js` (processBuyCommand) | เหมือนกัน |
| `transaction.service.js` (validateSell) | เหมือนกัน |
| `profit.service.js` | `getAssetProfit(..., portfolioId = null, ...)` |
| `webhook.controller.js` | `const portfolioId = parsed.params.portfolioId ?? null;` |

ปลายทาง:

```js
// asset.repository.js:75 (เดิม) — ternary 2 ทางที่ยุบ undefined กับ null เข้าด้วยกัน
return portfolioId ? base.eq('portfolio_id', portfolioId) : base.is('portfolio_id', null);
```

### 3.2 ทำไมมันไม่พังมาก่อนหน้านี้

**ก่อน `044` ข้อมูลจริงบน Production มี `portfolio_id = NULL` แทบ 100%**
(`migration 014` บอกไว้เองว่า *"Free-tier ไม่มี portfolio"*) → `.is('portfolio_id', null)`
บังเอิญตรงกับข้อมูลทุกแถวพอดี โค้ดจึงทำงานถูกมาตลอด **ด้วยความบังเอิญ ไม่ใช่ด้วยการออกแบบ**

`044` คือตัวที่ทำลายความบังเอิญนั้น

## 4. ⭐ บทเรียนที่มีค่ากว่าตัวบั๊ก — คำเตือนที่ครอบไม่ครบ

`assetResolution.service.js` **มีคำเตือนเรื่องนี้เขียนไว้เองอยู่แล้ว** ตั้งแต่ Stage 5:

> *"⚠️ ห้ามเขียน `brokerId: params.brokerId ?? null` ที่จุดใดก็ตามก่อนส่งเข้ามา —
> การทำแบบนั้นเปลี่ยน 'ยังไม่ได้ถาม' ให้กลายเป็น 'ตอบแล้วว่าไม่มีโบรก' เงียบๆ …
> → ประวัติแตกคนละ `asset_id` = บั๊กเดียวกับที่ migration 014 เคยแก้เป๊ะ"*

**แล้วโค้ดในไฟล์เดียวกันนั้นก็ไปทำผิดแบบเดียวกันเป๊ะกับ `portfolioId`** —
รวมถึง Default Parameter ที่อยู่ห่างจากคำเตือนไปแค่ 30 บรรทัด

### กฎที่ได้จากเรื่องนี้

> **คำเตือนที่ครอบไม่ครบ อันตรายกว่าไม่มีคำเตือน**
>
> เพราะคนอ่าน (รวมทั้ง AI) เห็นว่า *"มีคำเตือนเรื่องนี้อยู่แล้ว"* จึงสรุปว่า
> **"ตรวจแล้ว"** และไม่เอะใจกับมิติที่คำเตือนไม่ได้พูดถึง — ถ้าไม่มีคำเตือนเลย
> อย่างน้อยคนอ่านยังต้องคิดเองทุกมิติ

**สิ่งที่ทำ:** ขยายคำเตือนให้ครอบทั้ง `brokerId` และ `portfolioId` พร้อมเขียนกำกับว่า
**ถ้าเพิ่มมิติที่ 3 ในอนาคต (เช่น sub-account) ต้องมาขยายคำเตือนนี้ด้วยเสมอ**

## 6. Fix

ทำให้ `portfolioId` ใช้กติกาเดียวกับ `brokerId` ที่มีอยู่แล้ว (**ไม่ใช่ Pattern ใหม่**):

| ค่า | ความหมาย | พฤติกรรม |
|---|---|---|
| `undefined` | "ยังไม่ระบุ / พอร์ตไหนก็ได้" | ไม่กรอง `portfolio_id` เลย |
| `null` | "เจาะจงว่าไม่มีพอร์ต" | `.is('portfolio_id', null)` |
| `'<uuid>'` | เจาะจงพอร์ตนั้น | `.eq('portfolio_id', uuid)` |

1. `asset.repository.findAllByUserAndSymbol` — แยก 3 ทาง (เลิก ternary 2 ทาง)
2. `assetResolution.resolveOwnedAsset` — **ลบ Default `= null`** ออก
3. ลบ `?? null` ของ `portfolioId` ทุกจุด (`transaction.service` ×3 · `webhook.controller`)
4. `profit.service.getAssetProfit` — ลบ Default `= null`
5. เพิ่ม `AMBIGUOUS_ASSET_PORTFOLIO` — ถือ Symbol เดียวกันหลายพอร์ตแล้วไม่ระบุ
   → **ถาม/Reject ห้ามเดา** (กฎยืนข้อ 11)
   > ⚠️ **ข้อความเดิมของบรรทัดนี้เขียนว่า "ตรวจมิติพอร์ต *ก่อน* มิติโบรกเสมอ"
   > ซึ่งไม่จริงในโค้ดรอบที่ 1** — ดู § 10 (บั๊กรอบที่ 2)
6. สินทรัพย์ **ใหม่** ที่ไม่ระบุพอร์ต → ลงพอร์ต `is_default`
   (Invariant `044/045`: สินทรัพย์ทุกแถวต้องสังกัดพอร์ต)
7. ขยายคำเตือนใน Header ให้ครอบทั้งสองมิติ (ดู § 4)

## 10. ⭐ รอบที่ 2 — หางของบั๊กเดียวกัน (27 ส.ค. 2569)

> **นี่ไม่ใช่บั๊กใหม่** — เป็นบั๊กคลาสเดียวกันเป๊ะที่เหลือหางอยู่หลังการแก้รอบที่ 1
> พบตอนรีวิว `6cf6aa1` ด้วยการอ่านโค้ดจริง **ก่อน Deploy และก่อน Apply `044`**

### 10.1 บั๊ก

การแก้รอบที่ 1 ทำให้ `candidates` **ข้ามพอร์ตแล้วจริง** เมื่อ `portfolioId === undefined`
แต่ลำดับการตัดสินใน `resolveOwnedAsset` ยังเป็นแบบนี้:

```js
if (brokerId !== undefined) {
  const asset = candidates.find((a) => brokerKey(a.brokerId) === wanted) ?? null;
  return { asset, candidates };          // <-- return ตรงนี้
}
...
if (portfolioId === undefined) {          // <-- ด่านพอร์ตอยู่ "หลัง" จุด return ข้างบน
  if (portfolios.size > 1) throw AMBIGUOUS_ASSET_PORTFOLIO
}
```

**ระบุ `brokerId` มาเมื่อไหร่ = ข้ามด่านพอร์ตทั้งหมด** แล้ว `.find()` หยิบแถวแรก
ตาม `created_at` เงียบๆ

### 10.2 เคสที่พัง

ผู้ใช้ถือ **BTC @ Bitkub ในพอร์ต A** และ **BTC @ Bitkub ในพอร์ต B** — ถูกต้องตาม
`UNIQUE NULLS NOT DISTINCT (user_id, symbol, portfolio_id, broker_id)` ของ `046`
เพราะ `portfolio_id` ต่างกัน

1. ผู้ใช้ตอบโบรกไปแล้วว่า "Bitkub" (`brokerId = uuid`, `portfolioId` ยัง `undefined`)
2. `candidates` = 2 แถว ข้ามพอร์ต
3. `.find()` หยิบ **แถวแรก** เงียบๆ
4. เขียนธุรกรรมเข้าพอร์ตผิด → **ต้นทุนเฉลี่ยของทั้งสองพอร์ตเพี้ยนพร้อมกัน**

⚠️ **ไม่ใช่ Edge Case** — คนที่แยกพอร์ต "ระยะสั้น / ระยะยาว" แต่ใช้ Exchange เดียว
คือรูปแบบการใช้งานปกติมาก

### 10.3 ⭐⭐ บทเรียนข้อ 1 เกิดซ้ำ **ในไฟล์เดียวกัน เป็นครั้งที่สอง**

คอมเมนต์ที่เขียนไว้ในบล็อกด่านพอร์ตรอบที่ 1 คือ:

> *"── กำกวมมิติ 'พอร์ต' (**ตรวจก่อนมิติโบรกเสมอ**) ──"*

**โครงสร้างจริงไม่ได้ตรวจก่อน** เมื่อมี `brokerId` ส่งมา · และ § 6 ข้อ 5 ของเอกสาร
ฉบับนี้เองก็เขียนประโยคเดียวกันซ้ำอีก — คือ **เอกสาร Post-mortem ที่สรุปบทเรียน
"คำเตือนที่ครอบไม่ครบ" ไปทำผิดข้อนั้นเองในหน้าเดียวกัน**

> ### กฎที่ได้เพิ่ม (แข็งกว่าเดิม)
>
> คำว่า **"เสมอ" / "ทุกจุด" / "ที่เดียว" / "ทุกเส้นทาง"** ในคอมเมนต์ = **ข้อผูกพัน
> ที่ต้องพิสูจน์ด้วย `grep` จริง** ก่อน Commit ทุกครั้ง ไม่ใช่ด้วยความเชื่อ
>
> เหตุผล: ประโยคเหล่านี้คือสิ่งที่คนอ่านรอบหน้า (รวมทั้ง AI) ใช้ **ตัดสินใจว่า
> "ไม่ต้องตรวจซ้ำ"** — คอมเมนต์ที่โกหกจึงไม่ได้แค่ไร้ประโยชน์ แต่มัน **ปิดตา
> คนตรวจรอบถัดไป** ซึ่งคือกลไกที่ทำให้บั๊กเดียวกันรอดมาได้สองรอบ

### 10.4 ทำไมเทสต์ 18 เคสของรอบที่ 1 จับไม่ได้

ทุกเคสเป็น **"พอร์ตกำกวม แต่ไม่ระบุโบรก"** หรือ **"โบรกกำกวม แต่พอร์ตเดียว"**
— ไม่มีเคสไหน **ผสมสองมิติพร้อมกัน** เลยแม้แต่เคสเดียว

> **บทเรียน:** เทสต์ที่ครอบ "แต่ละมิติแยกกัน" ครบถ้วน **ไม่ได้แปลว่าครอบ
> จุดตัดของทั้งสองมิติ** — และบั๊กของ Resolution มักอยู่ที่จุดตัดเสมอ
> (จำนวนเคสที่ต้องครอบคือ **ผลคูณ** ไม่ใช่ผลบวก)

### 10.5 Fix

**ย้ายด่านพอร์ตขึ้นไปอยู่ก่อน `return` ทุกจุด** และให้ตัดสินจาก
*"ปลายทางที่ยังเป็นไปได้"* แทน `candidates` ดิบ:

```js
const matchedByBroker = brokerId === undefined ? candidates : candidates.filter(...);
// โบรกใหม่ที่ยังไม่เคยถือ -> ปลายทางคือแถวใหม่ ซึ่งลงพอร์ตไหนก็ยังเป็นไปได้หมด
const possible = matchedByBroker.length > 0 ? matchedByBroker : candidates;

if (portfolioId === undefined && new Set(possible.map(p)).size > 1) throw AMBIGUOUS_ASSET_PORTFOLIO;
if (brokerId !== undefined) return { asset: matchedByBroker[0] ?? null, candidates };
```

**ทำไมกรองโบรกก่อนแล้วค่อยตรวจพอร์ต แทนที่จะตรวจ `candidates` ทั้งชุดก่อนเสมอ**
(ตัดสินใจเองโดยตั้งใจ — RED-3 พิสูจน์ว่าจำเป็น):

ถือ BTC @ Bitkub ในพอร์ต A และ BTC @ Binance ในพอร์ต B — ผู้ใช้ตอบ "Bitkub" มาแล้ว
ปลายทางเหลือพอร์ต A **ทางเดียว** · ถ้าตรวจทั้งชุดก่อนจะถามพอร์ตซ้ำทั้งที่คำตอบมีทางเดียว
= เพิ่ม Latency บน Live Path โดยไม่จำเป็น (**กฎยืนข้อ 10**)

ผลลัพธ์ด้าน "ห้ามหยิบแถวแรกเงียบๆ" เหมือนกันทุกกรณี แต่ถามผู้ใช้น้อยกว่า

**ลำดับคำถามเมื่อกำกวมทั้งสองมิติ (2 พอร์ต x 2 โบรก)** — ยืนยันแล้วว่ายังถามพอร์ตก่อน:

| ผู้ใช้ตอบอะไรมาแล้ว | `matchedByBroker` | ผลลัพธ์ |
|---|---|---|
| ยังไม่ตอบอะไร | = `candidates` (4 แถว, 2 พอร์ต) | ถาม **พอร์ต** (คำถามที่ 1) |
| ตอบพอร์ตแล้ว | Repository กรองเหลือพอร์ตเดียว | ถาม **โบรก** (คำถามที่ 2) |
| ตอบโบรกแล้ว โบรกนั้นอยู่พอร์ตเดียว | 1 แถว | **ไม่ถามอะไรเลย** |
| ตอบโบรกแล้ว โบรกนั้นอยู่ 2 พอร์ต | 2 แถว | ถาม **พอร์ต** <- บั๊กเดิมอยู่ตรงนี้ |
