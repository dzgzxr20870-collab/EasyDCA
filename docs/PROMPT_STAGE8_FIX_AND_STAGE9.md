### ⭐ มติ Founder เพิ่มเติม (24 ส.ค. 2569) — อ่านให้จบก่อนเขียนโค้ด

หลักการ "อ่านได้ เขียนไม่ได้ ยกเว้นพอร์ตหลัก" **ยืนยันตามเดิม** แต่ต้องแยก "เขียน"
ออกเป็น **2 ชนิด** ซึ่ง § 8.1(ก) เดิมไม่ได้แยกไว้:

| การกระทำ | พอร์ตส่วนเกิน (หลัง Premium หมดอายุ) | เหตุผล |
|---|---|---|
| **เพิ่มของใหม่** — ซื้อ · เพิ่มสินทรัพย์ · บันทึกปันผล · Bulk Import · ย้ายสินทรัพย์เข้า | ❌ **บล็อก** | นี่คือการใช้ฟีเจอร์ Multi-portfolio ต่อโดยไม่จ่าย = สิ่งที่ Gate มีไว้กัน |
| **ลดของเดิม / แก้ให้ตรงความจริง** — **ขาย** · **ย้อนรายการล่าสุด (Undo)** · ย้ายสินทรัพย์ **ออก** ไปพอร์ตหลัก | ✅ **อนุญาตเสมอ** | ผู้ใช้ขายหุ้นจริงไปแล้วในโลกจริง ถ้าบันทึกไม่ได้ **พอร์ตจะโชว์ตัวเลขผิดถาวร** และผู้ใช้ "ออกจากพอร์ตที่ถูกล็อก" ไม่ได้เลย = ขังสินทรัพย์ไว้เป็นตัวประกันค่าสมาชิก |

> **ทำไมข้อนี้สำคัญกว่าที่คิด:** ถ้าบล็อกการขายด้วย ผู้ใช้ที่ไม่ต่ออายุจะติดอยู่ในสถานะ
> "พอร์ตแสดงว่ายังถือ BTC 0.5 อยู่" ตลอดไปทั้งที่ขายไปแล้ว — ตัวเลขกำไร/ขาดทุนที่เขาเห็น
> จะผิดถาวร ซึ่งขัดกับจุดยืนทั้งหมดของผลิตภัณฑ์ (บันทึกให้ตรงความจริง) และเข้าข่าย
> "เอาข้อมูลผู้ใช้เป็นตัวประกัน" ซึ่งอยู่คนละเรื่องกับการจำกัดฟีเจอร์
> การล็อกต้องหมายถึง **"โตต่อไม่ได้"** ไม่ใช่ **"ออกไม่ได้"**

**เพิ่มอีก 1 ข้อ — ผู้ใช้เลือกพอร์ตหลักเองได้:**
"พอร์ตที่ยังเขียนได้" ปัจจุบันตัดสินด้วย `created_at` เก่าสุด ซึ่ง Deterministic ดีแล้ว
แต่ **อาจไม่ใช่พอร์ตที่ผู้ใช้ใช้จริง** (พอร์ตเก่าสุดคือตัวที่ migration 044 Backfill สร้างให้
ซึ่งอาจแทบว่างเปล่า ส่วนพอร์ตที่เขาใช้จริงคือตัวที่สร้างทีหลัง)

→ ใช้ `portfolios.is_default` เป็นตัวตัดสินแทน **(ไม่ใช่ `created_at`)** เพราะ `is_default`
คือ "พอร์ตหลักของผู้ใช้" ตามความหมายอยู่แล้ว และผู้ใช้เปลี่ยนได้ (ถ้ายังไม่มีทางเปลี่ยน
ให้ **เพิ่ม `PATCH /portfolios/{id}` รองรับ `isDefault: true`** — Premium เท่านั้น
เพราะ Free มีพอร์ตเดียวอยู่แล้ว) · คง `created_at` + tie-break ด้วย `id` ไว้เป็น
**Fallback เมื่อ `is_default` หายไป** (Invariant พัง) ห้ามลบทิ้ง

### สิ่งที่ต้องทำ

1. **แก้คอมเมนต์ให้ตรงความจริงก่อนเป็นอย่างแรก** — ไม่ว่าจะเลือกทำข้ออื่นแค่ไหน
   คอมเมนต์ต้องไม่โกหกอีก
2. เปลี่ยน `getWritablePortfolioIds` ให้ยึด `is_default` เป็นหลัก (Fallback = `created_at`
   + tie-break `id`) — เขียนเหตุผลกำกับว่าทำไมถึงเปลี่ยน
3. เพิ่มด่านเข้าเส้นทาง **"เพิ่มของใหม่"** ทุกทาง (เว็บ · LINE · ปันผล · Bulk Import)
   — **ทางที่ถูกคือรวมด่านไว้จุดคอขวดร่วม ไม่ใช่แปะทีละ Controller** (ไม่งั้นจะกลับมา
   เจอปัญหาเดิมคือ "แปะครบ 4 ที่ ลืมที่ 5")
   → พิจารณาวางไว้ที่ `transaction.service.validateBuy` / จุดที่ resolve asset → portfolio
   ให้ครบทุก Caller ในคราวเดียว แล้วอธิบายในคอมเมนต์ว่าทำไมจุดนั้นคือจุดคอขวดจริง
4. **ห้ามบล็อก** `sell` / `undoLastTransaction` / การย้ายสินทรัพย์ **ออก**ไปพอร์ตหลัก
5. Error Code ใหม่ต้องมีข้อความไทยที่บอกทางออกได้จริง — ต้องสื่อว่า
   *"ยังขายและย้ายออกได้ปกติ"* ไม่ใช่แค่ "พอร์ตนี้อ่านได้อย่างเดียว" ซึ่งชวนให้เข้าใจว่า
   ทำอะไรไม่ได้เลย · และ **ห้ามใช้ภาษาที่ชี้นำการลงทุน** (กฎเหล็กข้อ 1)

### เทสต์ที่ต้องมี (Red-Green ทุกข้อ)

- Premium หมดอายุ + 3 พอร์ต → **ซื้อ**เข้าพอร์ตส่วนเกิน = ถูกบล็อก **ทั้งทางเว็บและทาง LINE**
- Premium หมดอายุ + 3 พอร์ต → **ขาย**สินทรัพย์ในพอร์ตส่วนเกิน = **ผ่าน**
- Premium หมดอายุ → **Undo** รายการล่าสุดที่อยู่ในพอร์ตส่วนเกิน = **ผ่าน**
- Premium หมดอายุ → **บันทึกปันผล**เข้าพอร์ตส่วนเกิน = ถูกบล็อก
- Premium หมดอายุ → **ย้ายสินทรัพย์ออก**จากพอร์ตส่วนเกินไปพอร์ตหลัก = **ผ่าน**
- Premium หมดอายุ → **ย้ายสินทรัพย์เข้า**พอร์ตส่วนเกิน = ถูกบล็อก
- **ต่ออายุแล้วกลับมาเขียนได้ทันที** โดยไม่ต้องทำอะไรเพิ่ม
- Free (พอร์ตเดียว) → พฤติกรรมต้อง **เหมือนเดิมทุกประการ** ไม่มีอะไรถูกบล็อกเพิ่ม
  ⚠️ ข้อนี้สำคัญที่สุดในทางปฏิบัติ — ผู้ใช้ Free คือคนส่วนใหญ่ของระบบวันนี้
  ถ้าพลาดจะบล็อกคนที่ไม่ควรโดนบล็อกทั้งฐาน
- Premium ที่ยัง Active → เขียนได้ทุกพอร์ต

## 🔴 งานที่ 2 — เพดานจำนวนพอร์ตเป็น check-then-insert ที่ไม่ Atomic

### สิ่งที่ตรวจเจอ

`portfolios.service.createPortfolio`:

```js
const limit   = entitlement.getActivePortfolioLimit(userRecord);
const current = await portfolioRepository.countByUser(userId);   // อ่าน
if (current >= limit) throw ...                                   // ตรวจ
return await portfolioRepository.create(userId, {...});           // เขียน ← มีช่องว่างตรงนี้
```

ผู้ใช้ Free กดสร้างพอร์ตสองแท็บพร้อมกัน → ทั้งคู่อ่านได้ `current = 1` → ผ่านการตรวจทั้งคู่
→ **ได้ 2 พอร์ต ทะลุเพดาน Free** และไม่มีอะไรใน DB กันไว้เลย

### ทำไมต้องแก้ ไม่ใช่ปล่อย

นี่คือเคสเดียวกับที่ **migration 035 (`create_asset_locked`) ถูกสร้างขึ้นมาแก้เป๊ะ** —
ในโปรเจกต์นี้มีทั้ง Pattern สำเร็จรูปและเทสต์ตัวอย่าง (`tests/assetLimitRace.test.js`)
อยู่แล้ว การปล่อยให้เพดานพอร์ตเป็น Pre-check ล้วนคือการถอยหลังจากมาตรฐานที่ทีมตั้งไว้เอง
(และ Entitlement คือหมวดเสี่ยงสูงตาม § 4)

### สิ่งที่ต้องทำ

สร้าง **migration 048** — `create_portfolio_locked()` RPC ตาม Pattern ของ `035` เป๊ะ:

1. `PERFORM 1 FROM users WHERE id = p_user_id FOR UPDATE` (Lock ที่ระดับ user
   เพราะ Invariant นี้มี Scope เป็นทั้ง user)
2. นับพอร์ตจริงใต้ Lock
3. Validate เพดาน → `RAISE EXCEPTION 'PORTFOLIO_LIMIT_REACHED'` พร้อม `DETAIL`
   รูปแบบเดียวกับ `035` (`limit=%s;current=%s`)
4. INSERT ใน Transaction เดียวกัน
5. `SECURITY DEFINER` + `SET search_path = public, pg_temp` + `REVOKE`/`GRANT`
   ให้ `service_role` เท่านั้น

**ข้อบังคับของ Migration นี้:**

- `p_portfolio_limit` ต้องรับมาจาก Caller **ห้าม Hardcode เลข 1/50 ใน SQL** —
  Single Source of Truth ของตัวเลขอยู่ที่ `entitlement.service.js` เหมือนที่ `035` ทำกับ
  `p_asset_limit`
- ต้องมี **VERIFY Query** ท้ายไฟล์ (Signature มีตัวเดียว · สิทธิ์เฉพาะ `service_role` ·
  จำนวนแถวเดิมไม่เปลี่ยน)
- ต้องมี **RED-GREEN ระดับ SQL** ท้ายไฟล์ (บล็อก `BEGIN … ROLLBACK`)
- ต้องมี **ROLLBACK PLAN** — ลำดับ Revert โค้ดก่อนแตะ DB เสมอ
- ⚠️ ตรวจก่อนว่า Invariant ของ `044/045` ("ทุก user มีพอร์ต Default 1 อันเป๊ะ")
  ยังจริงหลัง RPC นี้ — พอร์ตที่สร้างใหม่ **ต้องไม่ใช่** `is_default`
- คง Pre-check ฝั่ง JS ไว้ด้วย (ตอบผู้ใช้ได้เร็ว) แต่ **ด่านจริงคือ RPC** — เขียนคอมเมนต์
  ให้ชัดเหมือนที่ `035`/`046` ทำ

### เทสต์ที่ต้องมี

- แปลง Error ของ RPC → `PORTFOLIO_LIMIT_REACHED` / `PORTFOLIO_CAP_REACHED` ถูกต้อง
  (Free ต้องเห็นข้อความชวนอัปเกรด · Premium ที่ชน Cap 50 **ห้าม**เห็นข้อความชวนอัปเกรด
  เพราะเขาจ่ายเงินอยู่แล้ว — ตรรกะนี้มีอยู่แล้ว อย่าทำหาย)
- Race Condition test แบบเดียวกับ `assetLimitRace.test.js`
- Red-Green: ถอด Guard ใน RPC ออก → เทสต์ Race แดง

## กฎที่ห้ามละเมิด (ย้ำ)

1. **ห้าม Push / Merge / Deploy** จนกว่า Founder อนุมัติเป็นลายลักษณ์อักษร
2. **Immutable Ledger** — ห้าม `DELETE`/`UPDATE` transaction
3. **ห้ามลบข้อมูลผู้ใช้** ไม่ว่ากรณีใด (กฎเหล็กข้อ 2)
4. **Cross-User** — id ทุกตัวที่มาจาก Request ต้องยืนยันเจ้าของก่อนใช้ ผ่าน `queryForUser`
5. **ห้าม Silent Default** (กฎยืนข้อ 11) — กำกวมต้องถามหรือ Reject ไม่ใช่เดา
6. Migration ต้องล็อก `search_path` ตาม Pattern `028` · Apply + Verify บน Supabase
   ก่อน Deploy Code เสมอ (042–047 **ยังไม่ได้ Apply สักตัว** · 048 จะเป็นตัวถัดไป)
7. **DoD 4 ชั้น** ทุกงาน — ชั้นที่ 4 (Production Verification) ทำไม่ได้รอบนี้
   **ต้องระบุชัดว่ายังไม่ได้ Verify** · ห้ามเขียนว่า "ปิดสมบูรณ์"
8. **คอมเมนต์ต้องไม่โกหก** — ถ้าเขียนว่า "ใช้จากทุกจุด" ต้องใช้จากทุกจุดจริง
   ถ้ายังไม่ครบให้เขียนว่ายังไม่ครบและระบุว่าเหลือจุดไหน

## รายงานที่อยากได้ตอนจบ

0. **Model ที่ใช้จริงในแต่ละงาน** (ถ้าไม่ตรงตารางด้านบน ต้องบอกตรงๆ ห้ามเงียบ)
1. ตัวเลขเทสต์ **ก่อน/หลัง** ของแต่ละ Commit (ฐานปัจจุบัน **129 suites / 2,596**)

3. **ผลของ `grep -rn "assertCanWriteToPortfolio" src/` หลังแก้เสร็จ** — เพื่อพิสูจน์
   ด้วยของจริงว่าด่านครอบครบทุกเส้นทางแล้ว ไม่ใช่แค่บอกว่าครอบ

5. จุดที่ **ต่างจาก Design Doc / มติ โดยตั้งใจ** พร้อมเหตุผล
6. คำถามที่ต้องให้ Founder ตัดสิน **ถ้ามีจริงเท่านั้น**
